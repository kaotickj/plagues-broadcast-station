# Remembering a direct livestream

Choose **Direct livestream**, enter Destination and Stream key, select picture size and bitrate, then press **Save/update**. The key stays masked. A successful save explicitly says **Saved securely**. The profile restores on later launches with the same data folder. Restoring never connects or starts output: check the fields, then press **Start output** yourself.

**Restore saved** discards the current fields and reloads the selected saved profile. **Clear fields** clears only the current fields. **Forget saved** deletes both protected copies associated with this data folder and removes the local reference; it clears the streaming fields after successful deletion. A failure message means the operation did not finish: unlock the desktop keyring and retry. If protected copies were deleted but clearing the local reference failed, the message says so. Forget can also remove a protected copy left by an interrupted first save and recover a truncated or invalid reference in this version’s format. Symlink/directory references and valid unknown/future formats are refused; use the matching app version for a newer format.

The complete Destination can itself contain a private key in its path, query or login, so the **entire destination and key**, along with picture size and bitrate, are kept together in protected native credentials. They never enter playlists, portable profile exports, session JSON or ordinary settings. A small `broadcast-profile.json` in the chosen `--data-dir` contains only a schema number, selected slot and random non-secret revision token. Do not expect copied data folders or portable exports to carry secrets to another user, machine or differently located data folder.

Windows uses the explicit Windows Credential Manager backend; Linux uses the explicit Secret Service backend from the maintained [keyring library](https://keyring.readthedocs.io/en/stable/). Linux needs a running desktop Secret Service and an unlocked collection. The desktop may ask you to unlock it. There is no plaintext, alternate backend or automatic backend-selection fallback. If protected storage is missing, locked, full or unavailable, the fields remain usable for this session and the app does **not** claim they were saved. Native backend exception text is not shown. No keyring is contacted on a fresh startup with no saved reference. Credential operations run in a background worker and are disabled during output.

Saved credentials belong to the same OS user and the same canonical data-folder path. Two deterministic native slots, each with a separate per-data-folder service name, allow writing and verifying a replacement before atomically selecting it. A fresh random revision token binds the local selection to the exact protected payload, so a native backend’s stale fallback copy cannot restore an older target after primary credential loss. Windows persistence is explicitly local-machine, not enterprise roaming. A failed update keeps the previous active slot selected; a protected inactive copy can remain until a later save or Forget. An unavailable or invalid active slot is reported; the app never silently restores an older inactive slot. Cooperating app instances serialize save, restore and forget with a per-data-folder file lock. A busy instance reports that the operation must be retried. Existing native keyring access controls and the OS user account define the protection boundary; this is not protection against malware already running as that user.

Upgrading or rolling back the executable keeps the selected data folder and native credential namespace. Versions before 0.2.3 do not restore saved Broadcast credentials, but their data remains available when returning to 0.2.3. Recording still requires choosing an output filename and refuses to overwrite an existing file. This feature does not start streams automatically, download models or change audio capture behavior.
